
# Automotive Data Copilot PRD

## Overview
Automotive Data Copilot is a modern RAG-based agentic chatbot designed for automotive engineers to interact with measurement data files (.mf4, .mdf, .mat) through natural language. The system intelligently parses, analyzes, and visualizes automotive data, allowing engineers to gain insights without writing code. By combining state-of-the-art LLM technology with specialized automotive data processing, it dramatically reduces the time needed to analyze test drive data, compare measurements, and identify patterns or anomalies.

## Core Features

### File Ingestion and Management
- Upload and parse automotive measurement files (.mdf, .mf4, .mat)
- Extract metadata and signal information automatically
- Create a searchable index of signals with standardized naming
- Store parsed data efficiently for quick retrieval
- Support multi-file sessions with persistent context

### Natural Language Signal Processing
- Translate natural language queries into signal operations
- Intelligently map common terms to technical signal names
- Recognize domain-specific automotive terminology
- Support compound queries across multiple signals
- Maintain conversational context about previously referenced signals

### Interactive Visualization
- Generate time-series plots from natural language queries
- Support multiple visualization types (time series, XY plots, histograms, FFTs)
- Provide interactive Plotly charts with zoom, pan, and hover tooltips
- Allow signal comparison across multiple files
- Export high-quality plots for reports

### Signal Analysis and Transformation
- Apply filters and transformations via chat commands
- Perform statistical analysis on signal data
- Identify and extract specific maneuvers automatically
- Calculate derived signals based on engineering formulas
- Support frequency domain analysis (FFT, power spectrum)

### Multi-File Operations
- Synchronize timestamps across multiple recordings
- Compare similar maneuvers across different test runs
- Align signals with different sampling rates
- Identify anomalies between reference and test runs
- Generate comparative reports and visualizations

### RAG-Enhanced Knowledge Retrieval
- Retrieve relevant information from technical documentation
- Provide context-aware explanations of signal meanings
- Answer domain-specific questions using indexed knowledge base
- Cite sources for retrieved information
- Offer follow-up suggestions based on current analysis

## User Experience

### User Personas
1. **Test Engineer**: Conducts road tests and needs to quickly validate if test objectives were met
2. **Data Analyst**: Performs deep analysis on test data to extract insights and patterns
3. **Calibration Engineer**: Tunes vehicle systems based on measurement data
4. **Systems Engineer**: Validates system behavior against requirements using test data

### Key User Flows
1. **Data Exploration Flow**
   - Upload measurement file(s)
   - Ask about available signals
   - Request plots of interesting signals
   - Ask follow-up questions about observed patterns

2. **Analysis Flow**
   - Upload reference and test files
   - Request specific maneuver comparison
   - Receive anomaly detection report
   - Drill down into specific discrepancies

3. **Processing Flow**
   - Request signal filtering or transformation
   - View original vs. processed signal
   - Save or export processed results
   - Apply similar processing to other signals

### UI/UX Considerations
- Split-screen layout with chat interface and visualization area
- File management sidebar for uploaded data
- Interactive plot area with support for user selections
- Context-aware suggestions based on uploaded data
- Persistent session state for continuing analysis
- Responsive design that prioritizes visualization space
- Clear indication of processing status for long operations

## Risks and Mitigations

### Technical Challenges
1. **Large File Handling**
   - **Risk**: Performance issues with gigabyte-sized MDF files
   - **Mitigation**: Implement streaming parsers, lazy loading, and efficient Parquet conversion

2. **Signal Name Diversity**
   - **Risk**: Inconsistent signal naming across different files and OEMs
   - **Mitigation**: Build robust alias system and fuzzy matching with manufacturer-specific mappings

3. **Dependency Conflicts**
   - **Risk**: Version conflicts between agent-service-toolkit and automotive libraries
   - **Mitigation**: Use virtual environments, containerization, and careful dependency pinning

4. **Time Synchronization Accuracy**
   - **Risk**: Imprecise alignment of signals from different recordings
   - **Mitigation**: Implement multiple synchronization algorithms and validation metrics

### MVP Scoping
1. **Feature Creep**
   - **Risk**: Adding too many capabilities delaying usable product
   - **Mitigation**: Focus on core file parsing and basic plotting for initial release

2. **Complexity Balance**
   - **Risk**: Implementing either too simple or overly complex solutions
   - **Mitigation**: Build modular architecture that allows progressive enhancement

3. **Agent Understanding**
   - **Risk**: LLM agent struggles with automotive domain
   - **Mitigation**: Create specialized tools that handle complexity and provide structured outputs

### Resource Constraints
1. **Computational Resources**
   - **Risk**: Processing large files requires significant memory
   - **Mitigation**: Implement chunked processing and memory-efficient algorithms

2. **LLM API Costs**
   - **Risk**: Frequent LLM calls become expensive
   - **Mitigation**: Add caching layer and optimize prompt engineering

3. **Domain Expertise**
   - **Risk**: Building effective system requires automotive expertise
   - **Mitigation**: Collaborate with domain experts and build knowledge into tools

### Research Findings
1. **Common Pain Points**
   - Engineers spend 40%+ time on data wrangling
   - Signal naming inconsistency causes significant friction
   - Comparative analysis requires custom scripts for each project
   - Knowledge about signal meaning is often tribal/undocumented

2. **User Preferences**
   - Preference for interactive visualizations over static reports
   - Strong desire for natural language interface
   - Need for session persistence and reproducibility
   - Importance of exporting processed results

3. **Performance Benchmarks**
   - Typical automotive MDF files: 100MB to 10GB
   - Common signal count: 100-5000 per file
   - Typical sampling rates: 10Hz to 1000Hz
   - Expected processing times for initial parsing: <60s for 1GB file
